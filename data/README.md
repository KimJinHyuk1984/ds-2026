# 실습 데이터 안내

내용 기준은 [CURRICULUM.md](../docs/CURRICULUM.md)이다. **사용자가 기간 축소 후 재실행과 최종 검증을 완료했다. 현재 배포 파일은 353행 × 8열이며 강수량 결측은 200개다.** 사용자 최종 확인으로 따릉이 12개월 원본은 **38,286,211행**이며, 이용건수 결측 행 제외 0건·음수 0건이다. 이 숫자는 원본 기록 수이며 대여건수 합계가 아니다. 최종 CSV 커밋 대상은 `data/weather-bike/bike-daily.csv`로 확정한다.

## 학기 공통 파일

- 경로: `data/weather-bike/bike-daily.csv`
- 최종 대상 기간: **2024-03-01 ~ 2025-02-16**, 양 끝 포함 353일.
- 한 행: 날짜별 **서울 전체** 공공자전거 대여건수와 서울(108) 기상 관측값. 대여소별·시간대별 행은 최종 파일에 두지 않는다.
- 형식: 쉼표 구분, UTF-8 BOM(`utf-8-sig`), 날짜 오름차순, 인덱스 열 없음. 결측은 빈 필드.
- 재실행 결과 353행 × 8열이며 날짜 누락은 0일이다. 가짜 관측값이나 예시 행을 만들지 않았다.

| 최종 검증 항목 | 확정 수치 |
|---|---|
| 행·열 수 | 353행 × 8열 |
| 기간 | 2024-03-01 ~ 2025-02-16 |
| 날짜 누락 | 0일 |
| 강수량 결측 | 200개 |
| 대여건수 결측 | 0개 |
| 공휴일 | 19일 |

**기간을 2025-02-16까지로 줄인 이유:** 202502 따릉이 원본에 2월 16일 이후의 데이터가 없으며 재다운로드해도 동일하다고 사용자가 확인했다. 2월 17~28일은 집계 오류로 누락된 것이 아니라 원본 자체가 없는 기간이다. 기존 중간 파일은 유지하고 build-bike-daily.py에서 최종 기간만 선택해 병합한다. 이로써 대여건수가 비어 있던 마지막 12일을 최종 대상에서 제외한다.

압축 파일은 사용자가 풀어서 CSV만 해당 폴더에 둔다. 월별 원본은 한 달에 한 파일을 전제로 한다. 여러 달을 합친 파일이나 같은 달의 중복·분할 파일이 있으면 먼저 파일 구성과 합계 중복 여부를 확인해야 한다. 파일 이름은 강제하지 않으며 월은 원본 날짜 열로 판별한다.

`/source/`와 `/work-temp/`는 Git에서 제외한다. 2.5단계 후속 확인에서 원본 CSV 13개 모두 제외 대상이며 source/의 스테이징·추적 파일은 0개였다. 원본은 디스크에 보존한다. 이 처리 흐름의 CSV 커밋 후보는 `data/weather-bike/bike-daily.csv` 하나이며, `data/weather-bike/`의 다른 CSV도 제외한다.

이후 4~5주차 실습용 처리 단계별 CSV를 추가할 때는 해당 파일이 커밋 대상이 되도록 `.gitignore`도 수정해야 한다.

2026-09-09에 각 파일의 앞 4,096바이트를 읽어 cp949로 헤더가 해석되는 것을 확인했다. 전체 파일 디코딩·내용 검증 결과는 아니다. 스크립트는 UTF-8 BOM·cp949·euc-kr 및 BOM이 있는 UTF-16을 확인하고 앞쪽 안내·주석 행 다음의 헤더를 찾는다. 잘못된 문자를 대체하거나 오류 행을 무시하고 진행하지 않는다. 실제 내려받은 날짜와 이용 조건은 사용자가 아래 수집 기록에 남긴다.

## 공휴일 기준과 출처

**사용자가 대조·확인한 HOLIDAYS의 19개 날짜만** 공휴일여부=1로 표시한다. 일요일이라는 이유만으로 공휴일에 추가하지 않는다. 일요일 정보는 요일 열에 있으며, 회귀에서 일요일 효과와 공휴일 효과를 구분하기 위한 정의이다. 일요일 포함 옵션은 제거했다. HOLIDAYS에 있는 날짜는 일요일과 겹치더라도 공휴일로 표시한다. 이후 연도의 제도 변경을 소급 적용하지 않는다.

## 원본 컬럼명 대조표

ASOS 원본 순서는 `지점, 지점명, 일시, 평균기온(°C), 최저기온(°C), 최고기온(°C), 일강수량(mm)`이다. 위치가 아니라 이름으로 매핑하므로 최저기온이 최고기온보다 먼저 있어도 바뀌지 않는다. 기상 4개 열은 아래 부분 문자열을 찾고, 날짜·지점과 따릉이 열은 이름 후보로 찾는다. °·℃ 등 단위 문자를 매칭 조건에 넣지 않는다. 헤더 공백·BOM은 무시하고 후보가 둘 이상이면 임의 선택하지 않고 중단한다. 현재 따릉이 12개 파일 모두에서 `대여일자`, `이용건수`를 확인했다.

따릉이 원본의 부가 열은 연도에 따라 다르다. 2024년 파일에는 `이동거리(M)`, `이용시간(분)`이 있고 2025년 1~2월 파일에는 `이동거리`가 있다. 집계 스크립트는 날짜와 이용건수만 읽으므로 이 차이로 매핑을 바꿀 필요는 없다.

| 스크립트 | 정리할 열 | 현재 원본 컬럼 후보 |
|---|---|---|
| prepare-weather.py | 날짜 | 일시 / 날짜 / 관측일자 |
| prepare-weather.py | 평균기온 | 평균기온 (부분 문자열) |
| prepare-weather.py | 최저기온 | 최저기온 (부분 문자열) |
| prepare-weather.py | 최고기온 | 최고기온 (부분 문자열) |
| prepare-weather.py | 강수량 | 일강수량 (부분 문자열) |
| prepare-weather.py | 지점(선택) | 지점 / 지점번호 / 관측지점번호 |
| aggregate-bike.py | 날짜 | 대여일자 / 대여일시 / 기준일자 / 날짜 |
| aggregate-bike.py | 대여건수 | 이용건수 / 대여건수 / 이용 건수 / 대여 건수 |

ASOS의 지점 열이 있으면 108만 선택한다. 지점 열이 없으면 콘솔에 확인 요청을 출력하므로 사용자가 다운로드 지점을 확인해야 한다. 대여소 번호, 대여 시간, 성별·연령·이용권 등의 열은 집계 기준으로 쓰지 않는다. 소계·합계 행과 상세 행이 함께 들어 있는 자료는 이중 집계가 될 수 있으므로 사용 전에 원본의 행 의미를 반드시 대조한다.

`build-bike-daily.py`는 원본을 다시 읽지 않고 다음 중간 결과만 기대한다.

- 기상: 날짜, 평균기온, 최고기온, 최저기온, 강수량
- 따릉이: 날짜, 대여건수

## 실행 순서

**사용자가 기간 축소 후 재실행을 완료했다.** 아래는 같은 결과를 재현할 때의 절차다. 준비된 중간 파일을 사용하면 3번 build-bike-daily.py만 실행하며, 처음부터 데이터를 준비할 때는 세 단계를 순서대로 실행한다. Python 3.10 이상과 pandas가 필요하며, pandas 외 외부 Python 패키지는 사용하지 않는다. pandas가 없다면 사용할 Python 환경에 pandas만 설치한다.

64비트 Python 환경에서 다음과 같이 준비한다. pandas의 필수 하위 의존성은 pip가 함께 설치하며 별도 달력·CSV 패키지는 추가하지 않는다. [pandas 공식 설치 안내](https://pandas.pydata.org/docs/getting_started/install.html).

```powershell
py -3 --version
py -3 -m pip install pandas
```

저장소 루트의 PowerShell 기준:

```powershell
py -3 scripts/prepare-weather.py
if ($LASTEXITCODE -ne 0) { throw "기상 정리 실패: 다음 단계를 실행하지 마세요." }
py -3 scripts/aggregate-bike.py
if ($LASTEXITCODE -ne 0) { throw "따릉이 집계 실패: 다음 단계를 실행하지 마세요." }
py -3 scripts/build-bike-daily.py
if ($LASTEXITCODE -ne 0) { throw "최종 병합 실패: 오류를 확인하세요." }
```

Python 실행 명령이 `python`인 환경에서는 `py -3`을 `python`으로 바꾼다. 경로 기본값은 스크립트 위치를 기준으로 계산한다.

py 런처가 설치된 Python을 찾지 못하면 PowerShell에서 `& "설치된 python.exe의 전체 경로" scripts/build-bike-daily.py`로 실행한다. 이 세션에서는 Python이나 pandas 설치 여부를 추가로 검사하거나 스크립트를 실행하지 않는다.

| 단계 | 처리 | 결과 |
|---|---|---|
| 1 · prepare-weather.py | 헤더·인코딩 확인 → 서울(108)·기간 선택 → 날짜·기온 3종·일강수량 정리 | `work-temp/data-preparation/weather-daily.csv` |
| 2 · aggregate-bike.py | 월별 12개 순차 처리 → 파일별 100,000행 청크 → 날짜별 이용건수 합산 | `work-temp/data-preparation/bike-counts-daily.csv` |
| 3 · build-bike-daily.py | 중간 파일에서 2024-03-01~2025-02-16 선택 → 353일 날짜표에 1:1 왼쪽 병합 → 요일·공휴일 추가 | `data/weather-bike/bike-daily.csv` |

[공통 읽기 모듈 csvtools.py](../scripts/csvtools.py)는 인코딩·헤더 탐색, 날짜/수치 변환, 결측 요약과 저장을 공유한다. 별도로 실행하지 않는다. 중간 결과는 Git 제외 영역에 두며 최종 파일만 검토 후 배포한다. 재실행하면 해당 출력 파일을 교체하지만 원본에는 쓰지 않는다.

각 실행이 성공한 뒤 결측 개수와 컬럼별 요약을 확인한다. 앞 단계가 실패했다면 중단하고 원인을 수정한 후 그 단계부터 다시 실행한다. 이전 실행의 중간 결과가 남아 있을 수 있으므로 실패 후 바로 다음 단계를 실행하지 않는다.

### 단계별 성공 기준

모든 단계에서 현재 실행의 종료 코드가 0이고 마지막에 `[저장]`과 대상 경로가 출력되어야 한다. 파일이 이미 있다는 사실만으로 성공을 판정하지 않는다. 결측은 0개일 필요가 없다.

| 단계 | 확인할 내용 |
|---|---|
| 기상 정리 | weather-daily.csv에 날짜·평균기온·최고기온·최저기온·강수량 5열. 서울(108), 기간 내 날짜, 중복 날짜 0개. 강수량 공백은 빈 필드로 유지. 원본 날짜가 빠져 있으면 365행보다 적을 수 있음 |
| 따릉이 집계 | bike-counts-daily.csv에 날짜·대여건수 2열. 12개 월 모두 처리, 날짜별 최대 1행. 결측 행을 제외하고 유효한 이용건수를 합산하며 하루의 모든 행이 결측인 경우에만 빈 필드. 월별 제외 행 수, 전체 제외 행 수·비율, 대여건수 결측 날짜 목록 출력 |
| 최종 병합 | bike-daily.csv에 2024-03-01~2025-02-16 날짜 353행·지정 순서의 8열, UTF-8 BOM. 날짜 연속·중복 없음, 강수량 외 결측 0개인지 확인하고 대여건수 최소·최대 보고. HOLIDAYS 19개 날짜만 공휴일로 표시. 컬럼별 결측 요약과 최종 대여건수 결측 날짜 목록 출력 |

### 실패 시 확인할 곳

| No module named pandas | 스크립트를 실행할 Python으로 `py -3 -m pip install pandas` 실행. 다른 Python에만 설치하지 않았는지 확인 |
| 필수 컬럼 없음 / 후보 여러 개 | COLUMN_MAP과 SUBSTRING_COLUMNS 대조. 기온 열과 QC·시각 열이 함께 매칭되면 검색어를 구체화하거나 해당 열만 정확 비교하도록 설정 |
| UnicodeDecodeError / 헤더 탐색 실패 | prepare-weather.py의 ENCODING·HEADER_ROW·DELIMITER, 또는 aggregate-bike.py의 FILE_OVERRIDES 확인. header_row는 0부터 셈. UTF-8/cp949 등 실제 인코딩을 지정하고 오류 문자를 임의 삭제하지 않음 |
| 월별 CSV 12개 불일치 / 중복 월 / 여러 달 포함 | ZIP을 풀었는지, 한 달에 한 CSV인지, 202403~202502가 각각 있는지 확인. 분할본·합계본을 무작정 함께 넣지 않음 |
| 날짜·숫자 변환 실패 / 정수가 아닌 이용건수 | 오류 컬럼의 각주·합계 행·날짜 형식·단위·특수 결측 부호를 확인. 원본을 임의로 지우거나 0으로 바꾸지 말고 제공 기관 정의에 맞게 파싱 규칙을 조정 |
| 메모리 부족 | 64비트 Python 확인, CHUNK_SIZE를 100_000에서 20_000 등으로 낮춤. 전체 CSV를 합쳐 한꺼번에 읽지 않음 |
| PermissionError / 저장 실패 | 출력 CSV를 열어 둔 Excel 등을 닫고 경로 권한 확인. 실패 후 이전 파일을 새 결과로 사용하지 않음 |

헤더 탐색은 표준 라이브러리 csv.reader, 데이터 본문은 pandas.read_csv에 맡긴다. quotechar·quoting·doublequote를 재설정하거나 큰따옴표를 수동 제거하지 않는다. 대여소명에 쉼표가 있어도 표준 CSV의 인용 규칙으로 읽는다. 숫자 열 안의 천 단위 쉼표 정리는 CSV 파싱 후에만 수행한다. [pandas read_csv 문서](https://pandas.pydata.org/docs/reference/api/pandas.read_csv.html).

## 결측·이상치를 남기는 이유와 처리 범위

**4~5주차 실습을 위해 결측을 의도적으로 보존한다.** 결측을 인위적으로 만드는 것은 아니다.

### 현재 배포 파일의 강수량 결측 200개의 의미

**현재 배포 파일은 353일 중 강수량 결측이 200개다.** 212개는 축소 전 365일 기준의 수치다. 잘라낸 12일(2025-02-17 ~ 2025-02-28)이 모두 무강수일이었고 원본 강수량도 공백이었기 때문에, 기간 축소 후 결측이 212개에서 200개로 정확히 12개 줄었다.

사용자의 원본 검토에 따르면 이 결측은 비가 오지 않은 날을 뜻한다. 원본에서 무강수일을 공백으로 남겼으며 일부 무강수일은 수치 0으로 기록해 두 표현이 혼재한다. 따라서 이 파일에서 해당 결측의 실제 의미는 **강수량 0 mm**이다.

이는 **4주차 결측치 실습의 핵심 소재**이다. 학생이 이 결측을 평균으로 채우면 비가 오지 않은 날에 강수량을 만들어 넣게 되고, 해당 행을 삭제하면 유효한 무강수일 관측을 잃는다. 두 방법 모두 이 자료에서는 잘못된 처리다. 출처·기록 방식·데이터 맥락을 알아야 올바르게 결측을 처리할 수 있음을 가르친다.

실제 의미가 0임을 확인했더라도 **스크립트 단계에서는 이 결측을 채우지 않는다.** 원본 공백과 명시적인 0을 그대로 보존하고, 학생이 맥락을 확인한 뒤 처리 방법을 선택하는 활동에 남긴다.

- 강수량의 원본 공백은 결측으로, 원본에 기록된 수치 0은 0으로 유지한다.
- 기온·강수량·대여건수의 이상치를 제거하거나 보정하지 않는다. 음수·큰 수 등도 수치로 해석할 수 있으면 유지한다.
- 대여건수는 결측인 원본 행을 합산에서 제외하고 나머지 유효한 값으로 일별 합계를 계산한다. 그날의 모든 행이 결측인 경우에만 대여건수를 비워 둔다. 유효한 0이나 합계 0은 결측으로 바꾸지 않는다. 청크 경계를 넘어도 같은 규칙을 적용한다.
- 강수량은 독립변수·4주차 결측 실습 소재이므로 원본 결측을 그대로 보존한다. 회귀의 종속변수인 대여건수에는 위의 유효값 합산 정책을 적용한다.
- 월별로 합산에서 제외한 이용건수 결측 행 수를 출력한다. 전체 제외 비율의 분모는 12개 파일에서 읽은 데이터 행 수이며 헤더·빈 줄은 포함하지 않는다. 전체 제외 행 수·비율과 하루 전체가 결측인 날짜 목록을 출력하고, 마지막 병합 단계에서는 원본 행이 없는 날짜까지 포함한 최종 결측 날짜를 출력한다.
- 원본 날짜 행이 통째로 없으면 최종 파일에서 해당 관측 열을 비워 둔다. 일별 파일만으로 대여소·시간대 일부 행의 누락까지 자동 판정할 수는 없다.
- 빈 필드와 명시된 NA/N/A/NaN/NULL/None만 결측으로 읽는다. `-`, `-999`, `-9999` 같은 부호는 제공 기관 정의를 확인하기 전까지 임의 결측 처리하지 않는다. 숫자인 부호는 그대로 남고 숫자가 아닌 미정 부호는 오류로 알린다.
- 잘못된 날짜, 소계·각주, 중복 기상 날짜, 중복 월, 정수가 아닌 건수 등은 조용히 삭제·반올림하지 않고 중단한다.
- 출력에는 결측 개수와 모든 컬럼의 요약을 인쇄한다. 사용자 재실행으로 최종 강수량 결측 200개·대여건수 결측 0개를 확정했으며 가짜 결측을 만들지 않는다.

### 확정 학교와 급식 운영 차이 — 사용자 확인

| 학교명 | 표준학교코드 | 식사 종류·확인 사항 |
|---|---|---|
| 동양고등학교 | 7010965 | 중식·석식, 석식은 일부 날짜(122건) |
| 명덕고등학교 | 7010158 | 조식·중식·석식, 네 학교 중 유일하게 조식 제공·방학 중에도 급식 있음 |
| 영일고등학교 | 7010216 | 중식·석식, 석식은 일부 날짜(140건) |
| 세현고등학교 | 7010764 | 중식만 운영, 가장 적은 159일 |

이전의 ‘명덕고 외 세 학교는 중식만 운영’ 기록은 위 실측으로 정정한다. 명덕고는 방학에도 급식 기록이 있으며 동양·세현고의 마지막 기록은 2024년 12월, 영일고는 2025-01-02이다. 명덕고의 조식·방학 급식은 기숙사 운영과 관련 있을 가능성이 있다는 사용자 추정이며, 기숙사 여부나 운영 원인을 확인한 사실로 단정하지 않는다.

**2주차 3차시 관찰:** 명덕고 2024-03-04 급식인원은 조식 60명·중식 759명·석식 55명이다(원본 표시 60.0·759.0·55.0). 조·석식은 각각 중식의 10분의 1보다 적어 이용 대상이 다를 가능성을 시사한다. 학생이 관찰과 기숙사생 대상이라는 가설을 구별하고 추가 확인 근거를 생각하게 한다. 요리명은 메뉴 이름·괄호 속 숫자·HTML 태그가 한 칸에 함께 있다는 관찰까지만 다룬다. 2주차에는 정규식·텍스트 분리 코드를 제공하지 않으며 실제 처리는 4~5주차에 한다.

이 차이는 **3주차 데이터 통합 실습의 핵심 소재**다. 같은 API 컬럼을 사용해도 학교마다 식사 종류와 제공 일정이 달라 날짜별 행의 구성이 다르다. 명덕고·동양고·영일고는 한 날짜에 여러 식사 행이 있을 수 있으므로 ‘학교마다 하루 한 행’이라는 가정으로 무작정 합치면 건수·날짜 수를 잘못 해석한다. 학생이 직접 자료를 합치고 비교하면서 학교별 데이터 구조와 행의 단위를 확인해야 한다는 점을 경험하게 한다.

**스크립트에서 학교별 차이를 정규화하거나 식사 종류를 필터링하지 않는다.** --count와 전체 수집 모두 조·중·석식 전체를 그대로 조회하며 식사코드를 보존한다. 학교별 날짜 수를 맞추거나 일별로 합치지 않고 3주차의 통합·비교 기준 선택을 미리 대신 수행하지 않는다.

### 세현고 159일 — 13주차 설계 시 주의

세현고는 159일로 150일 기준을 겨우 충족한다. **13주차 연관분석에서 트랜잭션 수가 부족하여 규칙이 잘 도출되지 않을 수 있다.** 기준 충족이 충분한 규칙 발견을 보장하지 않는다.

대응 후보는 다음 두 가지이며 **13주차 설계 시 결정한다.**

- 4개교 데이터를 합쳐 하나의 트랜잭션 집합으로 구성한다.
- 데이터가 충분한 학교로 분석 대상을 한정한다.

현재는 어느 안도 선택하거나 필터로 구현하지 않는다. 트랜잭션 단위와 포함할 식사 종류도 13주차 설계에서 함께 정한다.

### 확정 파일과 컬럼

`data/neis/schools.csv`: 한 행에 한 학교, **4행 × 8열**. 표준학교코드는 문자열로 보존한다.

| 배포 컬럼 | API 필드 | 의미·단위 |
|---|---|---|
| 시도교육청코드 | ATPT_OFCDC_SC_CODE | 교육청 식별 문자열 |
| 표준학교코드 | SD_SCHUL_CODE | 학교 식별 문자열, 평균·합계의 대상 아님 |
| 학교명 | SCHUL_NM | 학교 이름 |
| 학교종류 | SCHUL_KND_SC_NM | 고등학교 여부 |
| 시도명 | LCTN_SC_NM | 소재 시도 |
| 설립구분 | FOND_SC_NM | 국립·공립·사립 등 범주 |
| 도로명주소 | ORG_RDNMA | 서울 소재 검증 및 동명이교 확인에 사용 |
| 홈페이지 | HMPG_ADRES | 학교 홈페이지 주소 |

`data/neis/meals.csv`: **1,504행 × 12열**, 한 행은 **학교 × 급식일자 × 식사코드**다. 같은 날 여러 식사가 있으면 여러 행이다. 학교×날짜만으로 중복을 제거하지 않는다. 기존 출력 이름 ‘식사명’은 요청한 ‘식사종류’로 맞췄고, 급식일자에서 계산한 ‘요일’을 추가했다.

| 배포 컬럼 | API 필드 | 의미·단위 |
|---|---|---|
| 시도교육청코드 | ATPT_OFCDC_SC_CODE | 학교 표와 연결할 코드 |
| 표준학교코드 | SD_SCHUL_CODE | 학교 표와 연결할 코드 |
| 학교명 | SCHUL_NM | 급식 제공 학교 |
| 급식일자 | MLSV_YMD | YYYYMMDD → YYYY-MM-DD |
| 식사코드 | MMEAL_SC_CODE | 1=조식, 2=중식, 3=석식. 문자열 |
| 식사종류 | MMEAL_SC_NM | 조식·중식·석식 등 NEIS 문자열 그대로 |
| 급식인원 | MLSV_FGR | 명, API의 값 표현을 그대로 보존 |
| 요리명 | DDISH_NM | 메뉴 원문. 줄 구분 태그·알레르기 번호 유지 |
| 원산지정보 | ORPLC_INFO | 원산지 원문 |
| 칼로리정보 | CAL_INFO | kcal 표기가 포함된 원문. 숫자로 강제 변환하지 않음 |
| 영양정보 | NTR_INFO | 영양 성분별 단위가 포함된 원문 |
| 요일 | 급식일자에서 계산 | 월·화·수·목·금·토·일, 기존 기상·따릉이와 같은 표기 |

두 파일 모두 UTF-8 BOM, 인덱스 열 없음, 표준 CSV 인용 규칙을 사용한다. **‘요리명’은 NEIS DDISH_NM 메뉴 원문 그대로다.** HTML 태그·알레르기 번호·공백·줄바꿈을 제거하거나 분리하지 않는다. HTML 태그 제거, 알레르기 번호 분리, 메뉴 분할은 모두 **4~5주차 학생 전처리 실습**이다. 원산지·영양정보도 원문을 보존한다. 식별용 코드는 문자열로 기록하고, 선택 컬럼의 null·미제공 값은 빈 필드로 남긴다. 식별 필드·날짜·메뉴가 비어 있으면 중단한다. CSV 인용/인코딩은 파일 저장 형식이며 메뉴 텍스트를 정제하는 작업이 아니다.

`.gitignore`에 `!/data/neis/*.csv`를 추가하여 NEIS 배포 CSV를 커밋할 수 있게 했다. 기존 규칙은 data/ 전체가 아닌 weather-bike/ 하위 CSV를 제한하고 있었다. source/ 원본 제외와 weather-bike/의 bike-daily.csv 단일 허용 규칙은 유지한다. 이번 수정에서는 CSV를 생성하거나 커밋하지 않았다.

### 가공 단계

1. 사전 확인 후 확정한 4개교를 교사 키로 schoolInfo에서 조회한다. 이름 완전 일치와 서울 고등학교 조건을 만족하는 후보 1개를 선택한다. 없거나 복수이면 중단한다.
2. 조회한 교육청·학교코드와 `MLSV_FROM_YMD=20240301`, `MLSV_TO_YMD=20250228`로 mealServiceDietInfo를 요청한다. 식사코드는 필터링하지 않아 전체 종류를 수집한다.
3. 학교 조회는 pSize=10, 전체 급식 수집은 최대 pSize=1000으로 요청한다. pIndex 증가로 모든 페이지를 읽고 서비스별 페이지 크기와 list_total_count·실제 누계를 대조한다. 기본 간격은 이전 요청 종료 후 1초다. 네트워크 타임아웃·HTTP 429·503만 최대 3회 추가 재시도(2·4·8초)한다. 429·503이어도 JSON이 아닌 응답은 진단 후 즉시 중단한다. 인증·API 업무 오류는 숨기거나 빈 결과로 처리하지 않는다.
4. 학교·기간·식사코드·중복 식별키를 검증한다. 급식일자를 YYYY-MM-DD로 기록하고 해당 날짜의 요일만 추가한다. 빈 값·월별 건수·학교별 및 식사별 고유 일수를 출력한다. 150일 미만이면 확인 경고를 출력한다. 식사종류·메뉴 원문과 학교별 운영 차이는 보정하거나 필터링하지 않는다.
5. 모든 학교의 수집이 성공한 뒤 두 CSV를 작성한다. 어느 학교든 기간 내 급식이 0건이면 저장 전에 중단한다. 기존 파일이 있으면 기본적으로 API 요청 전에 멈추며 `--overwrite` 지정 시에만 교체한다. 두 임시 파일 작성 후 각각 교체하므로 두 파일 전체의 동시 교체까지 보장하는 트랜잭션은 아니다.

### 교사 실행 방법

**Python 3.10 이상, 추가 패키지 설치 없음.** 수집기는 표준 라이브러리만 사용한다. 학생 Colab의 requests·pandas 예제와 별개이다. 저장소 루트에서 실행한다.

**사용자가 전체 수집을 완료했다. 아래는 수집 방법의 기록이며 이번 CSV 실습을 위해 재실행할 필요는 없다.**

```powershell
python .\scripts\collect-neis.py
```

확정 출력은 schools.csv 4행 × 8열, meals.csv 1,504행 × 12열이다. 키는 환경변수 NEIS_API_KEY 또는 숨김 입력으로 받는다. 재수집 시 학교별 건수를 위 확정 표와 대조하고, meals.csv의 식사종류·요일·요리명 원문을 확인한다. 기존 파일이 있으면 기본적으로 멈추므로 검토한 파일을 교체할 때만 --overwrite를 사용한다. 에이전트는 이 명령을 실행하지 않았다.

규모를 다시 확인해야 할 때는 다음 명령을 사용한다.

```powershell
python .\scripts\collect-neis.py --count
```

- 기본 범위는 동양·명덕·영일·세현고, 2024-03-01~2025-02-28 양 끝 포함이다. 교사 인증키를 환경변수 NEIS_API_KEY 또는 숨김 입력으로 받는다. 무인증 5건으로 학년 전체 규모를 판단할 수 없으므로 --count --no-key는 요청 전에 거절한다.
- 학교코드를 다시 조회·대조한 뒤 기간 전체 급식을 페이지별로 읽는다. 모든 페이지 누계, 학교·기간·식사코드, 페이지 안/사이의 중복 식별키를 검증한다. 메뉴 등 원문 전체를 누적하지 않고 한 페이지씩 처리하며 건수·고유 날짜·중복 검사용 식별키만 누적한다.
- 요약 표: **학교명 / 학교코드 / 총 건수 / 고유 급식일 수 / 조식·중식·석식 건수 / 150일 충족 여부**. 고유 급식일은 식사 종류와 관계없이 날짜 하나를 하루로 센다. 같은 날 세 식사가 있어도 총 3건·고유 급식일 1일이다.
- 월별 표에는 2024-03부터 2025-02까지 학교별 건수를 출력한다. **0건인 달도 표시**하므로 빈 구간을 확인할 수 있다. 0건의 원인이 미제공·방학·급식 미운영 중 무엇인지는 별도로 확인한다.
- 150일 미만 학교는 이름과 ‘미달’ 표시 및 기간/대상 조정 안내를 출력한다. 자료가 0건인 학교도 0건·0일로 표시한다. 건수 조회 완료와 수업 기준 충족은 구분하며, 기간·학교를 자동 변경하거나 곧바로 전체 수집하지 않는다.
- --count는 CSV·출력 폴더·임시 파일을 만들거나 기존 CSV를 변경하지 않는다. 기존 파일이 있어도 규모 확인이 가능하다. 일반 API 오류 진단·헤더·인증키 정제·요청 간격·재시도 정책을 그대로 사용한다.
- --schools·--start·--end·--page-size·--interval은 규모 확인에도 적용된다. 조정은 사용자 검토 후 수행한다. --count·--check·--minimal은 서로 동시에 지정할 수 없다. --output-dir·--overwrite는 규모 확인에 쓰이지 않는다.

이후 진단이 필요하면 동양고 하나만 최소 조건으로 조회할 수 있다.

```powershell
python .\scripts\collect-neis.py --minimal
```

- 요청 대상은 schoolInfo의 동양고등학교 하나다. **Type=json → ATPT_OFCDC_SC_CODE=B10 → SCHUL_NM=동양고등학교 → KEY** 순서로 네 파라미터만 보낸다. 키는 기존 환경변수/숨김 입력·정제 절차를 사용한다.
- SCHUL_KND_SC_NM·pIndex·pSize는 최소 요청에서 전송하지 않는다. 정상 응답 시 마스킹한 요청 URL·HTTP 상태·전체 응답 본문·반환 건수를 출력하고 종료한다. 다른 학교·급식·추가 페이지 조회, CSV/폴더 생성은 없다. 정상 요청은 1회이며 타임아웃·429·503의 제한된 재시도 정책은 공통으로 적용한다.
- 일반 조회와 동일한 REQUEST_HEADERS를 사용한다. --minimal·--check·--count는 동시에 지정할 수 없다. --schools·기간·페이지 크기·출력 옵션으로 최소 요청 구성을 바꾸지 않는다. 나머지 파라미터를 자동으로 늘려 요청하지 않는다.
- 인증키 없는 비교가 필요하면 `python scripts/collect-neis.py --minimal --no-key`를 사용한다. 이 조합은 KEY도 제외한 세 파라미터만 전송한다.

먼저 인증키 없이 사전 확인하여 인증키 사용 여부에 따른 차이를 비교한다. 이 모드에서는 환경변수를 읽거나 키를 입력받지 않고, 요청에서 KEY 파라미터를 아예 제외한다.

```powershell
python .\scripts\collect-neis.py --check --no-key
```

이어서 같은 학교·날짜를 인증키로 확인한다. 환경변수 NEIS_API_KEY가 없으면 인증키를 숨김 입력으로 받는다.

```powershell
python .\scripts\collect-neis.py --check
```

- --check는 현재 후보 5개교(기본 4개교+예비 대일고)를 조회한다. 학교코드 조회 성공/실패·표준학교코드·각 날짜의 데이터 유무 및 급식 종류를 표로 출력한다. 있음(조·중·석)에서 실제 반환된 종류만 표시하며, 학교/데이터 검증 오류는 ‘확인 실패’, 학교 조회 실패 뒤의 급식은 ‘조회 안 함’으로 표시한다. 정상적인 0건은 오류와 구분한다. 재시도할 수 없는 요청 오류나 재시도 한도 초과는 진단 후 전체 --check를 즉시 중단하고 종료 코드 1로 끝낸다. 이 경우 표는 중단 전까지의 일부 결과만 남는다.
- CHECK_DATES 기본값은 **2024-03-06, 2024-09-04, 2025-01-08**이다. 각 월의 수요일 하루씩만 조회하며 급식 요청은 FROM=TO이다. schoolInfo는 인증 여부와 관계없이 pSize=10으로 요청한다(무인증 반환 상한은 여전히 5건). 급식은 키가 있으면 pSize=3, --no-key이면 pSize=5이며 모두 pIndex=1이다. 급식은 실제 하루의 조·중·석 최대 3행인지 검증한다. 다른 날짜나 다음 페이지를 자동 조회하지 않는다.
- --no-key는 --check 또는 --minimal과 함께 사용한다. 학기 전체 수집에는 교사 키가 필요하며 무인증 5건 표본을 전체 데이터로 저장하지 않는다. 일반 schoolInfo의 SCHUL_KND_SC_NM=고등학교 조건은 인증 여부와 관계없이 유지하고, --minimal에서만 제외한다.
- 현재 --check의 정상 요청은 학교 5회+급식 15회로 **총 20회**다. 기본 요청 간격 대기만 약 19초이며 응답 시간이 더해진다. 학교코드 조회가 실패하면 해당 학교의 급식 요청은 생략한다. 최초 6개교 확인의 24회와 구분하며, --count는 전체 기간의 페이지 수에 따라 요청 횟수가 달라진다. 실제 요청 횟수·소요 시간은 마지막에 표시한다.
- **없음은 해당 하루의 응답 0건이다.** 방학·급식 미운영 때문일 수 있으므로 그 달이나 학년도 전체의 자료 부재로 단정하지 않는다. ‘있음’도 학교별 150일 이상을 보장하지 않는다. 결과를 검토한 뒤 최종 학교·기간을 정하고 전체 수집 결과의 일수를 따로 확인한다.
- 출력 폴더·CSV·임시 파일을 생성하지 않고 기존 CSV도 변경하지 않는다. --check에서는 --schools, --start, --end, --page-size, --output-dir, --overwrite 등 전체 수집 옵션을 적용하지 않는다. 후보·확인일은 상단 상수로 바꾸며 --interval은 두 모드 모두에 적용한다.

--count의 학교별 150일 기준과 월별 구간을 검토한 뒤 전체 수집을 수행한다.

```powershell
python .\scripts\collect-neis.py
```

인증키 사용 모드에서 환경변수 `NEIS_API_KEY`가 없으면 터미널에서 키를 숨김 입력으로 받는다. 두 입력 경로 모두 공백·개행·탭·작은/큰따옴표(굽은 따옴표 포함)·BOM을 제거한다. 정제 후에는 값 대신 길이만 출력하며 보통 길이인 32자와 다르면 경고한다. 길이만 다르다는 이유로 막지는 않지만, 빈 값·sample·자리표시자는 거절한다. 길이가 32자여도 유효한 키임을 보장하지 않는다. 키를 코드나 `--key` 인자에 넣지 않는다. 환경변수로 전달하려면 다음처럼 명령 이력에 실제 키를 쓰지 않고 입력한다.

```powershell
$neisCredential = [pscredential]::new("NEIS", (Read-Host "교사 인증키" -AsSecureString))
$env:NEIS_API_KEY = $neisCredential.GetNetworkCredential().Password
try {

    Remove-Item Env:\NEIS_API_KEY -ErrorAction SilentlyContinue

}
```

### HTTP·RESULT 오류 진단

사용자 보고: --check 실행 중 HTTP 500. 브라우저에서 KEY 없이 요청하면 SCHUL_KND_SC_NM의 유무와 관계없이 정상 동작했다. 해당 조건은 유지하며 인증키 문제를 가능성으로 두고 --check --no-key와 --check를 비교한다. 아직 인증키가 원인이라고 확정하지는 않는다. 현재는 HTTPError를 닫기 전에 본문 전체를 읽고, 각 실패 시도마다 아래를 출력한다.

후속 사용자 확인: 인증키 정제 후 32자 출력과 재시도 중단은 정상 동작했으나 HTTP 500은 지속된다. 소스에서 지정된 브라우저 헤더가 없고 학교 사전 조회가 1000건임을 확인하여 보완했다. 모든 요청은 상단 REQUEST_HEADERS의 User-Agent(Mozilla/5.0 Windows 10 x64·AppleWebKit/537.36·Chrome/120.0.0.0 Safari/537.36), Accept(application/json, text/plain, */*), Accept-Language(ko-KR,ko;q=0.9)를 공통 Request 생성부에서 사용한다.

일반 schoolInfo 파라미터 순서는 **Type → ATPT_OFCDC_SC_CODE → SCHUL_NM → SCHUL_KND_SC_NM → KEY → pIndex → pSize**로 고정했다. --no-key이면 KEY만 제외한다. 최소 요청은 위 실행 방법의 네 항목만 전송한다. 이 변경은 사용자 지정 브라우저 조건을 맞추기 위한 것으로, 헤더·페이지 크기·순서가 HTTP 500의 원인이라고 확정하지 않는다.

- HTTP 상태, 시도 번호, 실패 유형.
- 실제 요청의 전체 URL. KEY는 앞뒤 3자만 남겨 `abc...xyz` 형태로 가린다. 길이가 6자 이하이면 `***`로 전부 가린다. 한글 학교명의 URL 인코딩도 그대로 확인할 수 있다.
- 응답 본문 전체. 길이 제한이나 생략을 두지 않으며, 본문에 반사된 인증키의 원문·URL 인코딩·JSON/HTML 이스케이프 표현도 마스킹한다. 서버 지정 문자셋, UTF-8, CP949 순으로 해석을 시도한다. 연결이 끊겼으면 수신된 일부임을 표시하고, 응답 미수신과 빈 본문도 구분한다.
- `RESULT.CODE`, `RESULT.MESSAGE`를 별도 줄로 출력한다. JSON 최상위/중첩 head의 RESULT와 XML RESULT를 찾는다. HTML 등에서 RESULT를 찾지 못하면 ‘찾을 수 없음’으로 표시하고 위 본문으로 확인한다.
- HTTP 500뿐 아니라 HTTP 200의 RESULT 업무 오류·응답 형식 오류, JSON 해석 실패에도 같은 진단을 제공한다. 정상적인 자료 없음(INFO-200)은 기존처럼 0건으로 처리한다. 재시도는 네트워크 타임아웃·429·503만 허용한다. HTML/XML 등 JSON이 아닌 응답은 429·503이어도 즉시 중단한다. HTTP 500, DNS·인증서·연결 거부 오류, 불완전 응답, RESULT 업무 오류도 재시도하지 않고 사전 확인 전체를 중단한다. 진단의 XML RESULT 파싱은 원인 확인용이며, XML 응답으로 수집을 계속하지 않는다. --check는 CSV를 저장하지 않는다.

### 재수집 시 참고 — 규모·시간과 성공 기준

- 현재 확정 CSV는 학교 4행과 급식 1,504행이다. 재수집 결과가 위 학교별 실측 건수와 다르면 API 제공 자료의 변화 등을 확인한다. 수치를 맞추려고 행을 생성·삭제하지 않는다.
- 학교 조회와 급식 조회가 각각 한 페이지이면 4개교에서 정상 요청 8회이다. 기본 간격 대기 약 7초에 응답 시간이 더해진다. 요청당 1~10초라고 가정하면 약 15~90초, 재시도나 추가 페이지가 있으면 더 걸린다. 실제 소요 시간과 요청 수는 마지막 줄에 출력된다.
- 성공 검토: 확정한 4개교와 코드·주소 일치, 기간 밖 행·학교/날짜/식사 중복 0개, 모든 페이지 누계 일치, 학교별 고유 급식일 150일 이상인지 확인한다. 13주차에 중식만 사용할 경우 **중식 일수도 별도 확인**한다. 150일 경고가 있으면 저장 성공과 수업 데이터 충족을 구분한다.
- `INFO-200` 또는 0건: 날짜·학교코드·2024학년도 제공 여부를 확인한다. 연도를 자동 변경하거나 표본 5건으로 대체하지 않는다. 과거 자료가 없으면 데이터 확보 경로를 사용자와 다시 정한다.
- 인증/요청 오류: NEIS에서 발급한 교사 키인지 확인한다. 무인증 수집으로 자동 전환하지 않는다. 오류 코드는 공식 명세에서 확인한다.
- 짧은 페이지·누계 불일치: 유효한 키와 pSize 제한을 확인한다. 동일 페이지 반복이나 제공 자료 변경 가능성을 확인한 뒤 재실행한다.
- 타임아웃·JSON 응답의 429·503: 자동 재시도 후에도 실패하면 잠시 뒤 실행하거나 요청 간격을 늘린다. HTTP 500·비JSON 응답·그 밖의 연결 오류는 재시도 없이 중단하므로 진단 본문과 무인증 비교 결과를 먼저 확인한다. 파일 접근 오류는 Excel 등에서 기존 CSV를 열고 있는지 확인한다.
