미니 프로젝트 1 — 전처리와 판단 근거

16–18차시

원본 급식 데이터에서 질문의 답을 찾고, 내 처리의 이유와 한계를 함께 남깁니다.

과제 안내와 목표

“나는 무엇을 바꾸었고, 왜 그렇게 판단했는가?”

이번 주에는 4~5주차에서 배운 방법을 직접 적용해 Colab 노트북 하나를 만듭니다. 급식 원문에서 메뉴를 나누고, 하나의 질문에 답하고, 내 처리의 근거와 한계를 설명합니다.

  • 원본 급식 데이터를 메뉴당 한 행으로 전처리하고 선택한 질문에 코드로 답할 수 있다.
  • 괄호 처리의 판단 근거·예상과 달랐던 부분·자기 방법의 한계를 실제 사례와 함께 설명할 수 있다.
  • 코드·출력·마크다운을 포함한 Colab 노트북 하나로 과정을 공유할 수 있다.

평가의 핵심은 자기 방법의 한계를 알아차리는 일입니다. 잘못된 결과를 발견하고 설명하는 과정도 중요한 성과입니다. 교재 대응이 없는 프로젝트 주차입니다.

원본 데이터 받기

원본 meals.csv 내려받기1,504행 × 12열 · 실제 기록 2024-03-04~2025-02-28 · UTF-8 BOM

한 행은 한 학교·한 날짜·한 식사의 기록입니다. 요리명 컬럼에는 여러 메뉴와 구분 표시·괄호 정보가 함께 있습니다. 원본을 읽는 셀부터 메뉴 분리·검증·질문 답변까지 직접 남깁니다.

노트북 이름은 학번_이름_미니프로젝트1.ipynb로 저장합니다. 아래 시작 코드는 그대로 사용해도 됩니다. 이후 전처리와 질문 답변 코드는 자신이 작성합니다.

import pandas as pd

url = "https://kimjinhyuk1984.github.io/ds-2026/data/neis/meals.csv"
meals = pd.read_csv(url, encoding="utf-8-sig", dtype={"표준학교코드": str})
print(meals.shape)
display(meals.head())

(1504, 12)와 요리명 원문을 확인합니다. 처리 전 표를 보존하고 작업 결과를 대조할 수 있게 준비합니다.

차시별 진행 안내

1차시 · 메뉴 하나당 한 행으로

  1. 원본을 읽고 메뉴를 어떤 단위로 나눌지 정합니다.
  2. 4~5주차에서 배운 방법을 적용해 메뉴를 분리하고 괄호를 처리합니다.
  3. 실제 원문과 처리 결과를 나란히 보며 사라진 정보·남은 정보·잘못 나눈 항목을 찾습니다.
  4. 판단한 이유와 예상과 달랐던 부분을 그때그때 마크다운 셀에 적습니다.

차시 끝 점검: 원본에서 처리 결과까지 실행되는 코드와, 실제 사례를 대조한 기록이 있는가?

2차시 · 무엇을 세었는지 설명하기

  1. 아래 세 질문 중 하나를 고르거나, 원본 데이터로 답할 수 있는 자기 질문을 만듭니다.
  2. 대상·기간·식사 종류·메뉴 분류·집계 기준을 먼저 마크다운에 적습니다.
  3. 코드를 작성해 표 또는 그래프로 결과를 출력합니다.
  4. 결과와 연결되는 답을 한 문장으로 쓰고, 처리 기준을 바꾸면 답이 달라질 수 있는지 점검합니다.

차시 끝 점검: 선택한 질문과 코드의 계산 대상이 일치하며, 출력에서 답을 확인할 수 있는가?

3차시 · 결과와 한계를 함께 설명하기

  1. 코드 셀과 마크다운 셀의 순서를 정리합니다.
  2. 괄호 처리 근거·예상과 달랐던 부분·내 방법의 한계가 구체적인 원문 사례와 연결되는지 확인합니다.
  3. 노트북을 처음부터 순서대로 실행해 코드와 출력이 맞는지 대조합니다.
  4. 질문 한 문장 → 결과 한 가지 → 판단 근거와 한계 순서로 짧게 공유합니다.

차시 끝 점검: 실행 결과와 설명을 함께 담은 노트북을 파일 또는 공유 링크로 Google Classroom에 제출할 준비가 되었는가?

세 질문 중 하나 고르기

① 4개 학교 중 김치류가 가장 자주 나오는 학교는?

김치류에 무엇을 포함할지, “자주”를 어떤 기준으로 비교할지 스스로 정합니다.

  • 포함·제외한 실제 메뉴 사례를 설명할 수 있는가?
  • 무엇을 한 번으로 세었으며 학교별 기록량 차이를 어떻게 고려했는가?
  • 식사 종류나 기간이 다른데도 비교할 수 있는 범위는 어디까지인가?

② 알레르기 번호가 가장 많이 붙는 메뉴 top 10은?

메뉴별로 붙은 번호를 어떻게 세고 순위를 정했는지 설명합니다.

  • 같은 메뉴가 여러 번 나오거나 날짜에 따라 번호가 다르면 어떤 기준으로 대표했는가?
  • 번호가 붙은 개수와 메뉴의 제공 횟수를 구별했는가?
  • 번호 미표기·같은 번호의 반복·동률을 어떻게 다루었는가?

③ 우리 학교(동양고) 급식에 가장 자주 나오는 국·찌개류는?

동양고등학교 자료에서 국·찌개류의 범주를 정하고 등장 빈도를 비교합니다.

  • 국·찌개류로 분류한 기준과 경계에 있는 실제 메뉴는 무엇인가?
  • 서로 비슷하지만 이름이 다른 메뉴를 어떻게 다루었는가?
  • 분석한 식사 종류·기간과 이 결과가 말해 주는 범위를 적었는가?

자기 질문으로 바꾸어도 됩니다

세 질문을 모두 할 필요는 없습니다. 대신 궁금한 질문 하나를 만들고, meals.csv의 컬럼으로 답할 수 있는지 먼저 확인합니다.

사용할 컬럼·비교 대상·집계 단위를 적고 코드로 확인 가능한 질문으로 좁힙니다. 데이터에 없는 정보가 필요하면 무엇을 확인할 수 없는지 구별합니다. 확장 질문에도 같은 산출물 요구사항과 루브릭을 적용합니다.

산출물 · Colab 노트북 하나

코드만 제출하면 충분하지 않습니다

코드만으로는 처리 과정을 이해했는지 확인하기 어렵습니다. 원본에서 출발한 코드·실행 출력·판단을 설명하는 마크다운 셀을 한 노트북 안에 담습니다.

  1. 내 질문과 기준: 선택한 질문, 분석 대상, 무엇을 세었는지.
  2. 처리 과정: 원본 읽기부터 메뉴 분리·괄호 처리까지의 코드와 원문/결과 대조.
  3. 질문에 대한 답: 계산 코드, 결과 표 또는 그래프, 결과를 해석한 문장.
  4. 판단과 성찰: 아래 세 가지를 마크다운으로 작성한 기록.

마크다운은 처리한 코드와 실제 출력 옆에 배치합니다. 노트북 하나에 정리하고 이름은 학번_이름_미니프로젝트1.ipynb로 지정합니다.

반드시 써야 하는 세 가지

  • 괄호를 어떻게 처리했고, 왜 그렇게 판단했는가? 실제 원문과 내 처리 결과를 제시하고 선택한 이유를 설명합니다.
  • 처리 과정에서 예상과 달랐던 부분은 무엇인가? 처음 예상, 실제로 확인한 결과, 그 차이를 기록합니다.
  • 내 방법의 한계나 잘못 처리된 사례는 무엇인가? 구체적인 사례와 원인, 분석 답에 미칠 영향을 설명합니다.

수정했다면 처음 실패한 결과와 바꾼 이유도 남깁니다. 오류를 발견하지 못했다면 실제로 점검한 사례와 아직 확인하지 못한 범위를 적습니다. 실패 사례를 만들어 낼 필요는 없습니다.

Google Classroom으로 제출하기

파일명 규칙은 학번_이름_미니프로젝트1.ipynb입니다. 아래 두 방법 중 하나로 해당 과제에 제출합니다.

  • 파일 제출: Colab 노트북을 .ipynb 파일로 내려받아 Google Classroom 과제에 첨부합니다.
  • 링크 제출: Colab 공유 설정을 “링크가 있는 모든 사용자”로 바꾸고 보기 권한을 허용한 뒤, 공유 링크를 Google Classroom 과제에 첨부합니다.

공유 링크만 제출하고 접근 권한을 열지 않으면 교사가 노트북을 열 수 없습니다. 링크로 제출할 때도 노트북 이름은 같은 규칙으로 지정하고, 제출 전에 공유 권한을 확인합니다.

평가 루브릭

4번 ‘한계 인식’을 가장 중요하게 봅니다.

“내 방법으로는 시리얼(스페셜K외)가 잘못 처리되었다”처럼 스스로 문제를 발견한 학생은 처리의 의미를 이해한 것입니다. 실제 원문과 잘못된 결과를 보여 주고, 왜 문제가 되며 답에 어떤 영향을 주는지 설명하세요.

처리가 완벽하지 않아도 한계를 근거와 함께 설명하면 4번에서 ‘상’을 받을 수 있습니다. 오류를 모두 고치는 것보다 무엇을 놓쳤는지 알아차리는 일이 이 항목의 핵심입니다. 전처리 수행과 질문 답변은 각각의 기준으로 평가합니다.

미니 프로젝트 1 평가 기준
평가 항목상중하
1. 전처리 수행메뉴당 한 행으로 분리하고, 필요한 메뉴 정보를 보존해 괄호를 처리·검증했다.분리·괄호 처리를 시도했으나 일부가 누락되거나 검증이 부족하다.원본에서 처리한 과정이 없거나, 메뉴 분리·괄호 처리를 확인하기 어렵다.
2. 판단 근거처리 기준과 선택 이유를 실제 사례에 연결해 설명했다.무엇을 했는지는 적었으나 이유나 사례가 부족하다.처리 이유를 설명하지 않았거나 코드만 제시했다.
3. 질문 답변정한 기준대로 코드와 출력을 제시하고 질문에 맞는 답을 설명했다.관련 결과는 있으나 집계 기준이나 질문과의 연결이 불명확하다.코드로 도출한 결과 또는 질문에 대한 답이 없다.
4. 한계 인식
가장 중요		실제 점검 사례로 한계·실패 원인과 결과에 미칠 영향을 설명했다.한계는 적었으나 구체적인 사례나 영향 설명이 부족하다.한계 기록이 없거나, 점검 근거 없이 문제가 없다고 단정했다.
